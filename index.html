2
What is the difference between AWS Glue, Lambda, and Step Functions? When do you use each?
▼
  • Lambda: Stateless, event-driven compute for short-lived tasks (under 15 min). I used it for data ingestion triggers, light transformations, and API calls. Best for lightweight, reactive processing.
  • Glue: Managed Spark service for large-scale data transformation. I used it for PySpark ETL jobs that processed millions of billing records — schema inference, cleaning, enriching. Best for heavy batch ETL.
  • Step Functions: Orchestration layer that sequences tasks into state machines. I used it to chain Lambda and Glue tasks with retries, parallel branches, and error handling. Best for multi-step workflows that need reliability and visibility.

In practice I used all three together: Step Functions orchestrated, Lambda handled triggers and small transforms, Glue handled bulk data processing.

Explain Databricks and how it differs from AWS Glue.
▼

Both are Spark-based data processing platforms, but with key differences:

5
What is Hadoop and how does it compare to Spark?
▼
  • Hadoop (HDFS + MapReduce): Stores and processes data in batches across a cluster. MapReduce writes intermediate results to disk — making it slower. HDFS provides distributed, fault-tolerant storage. YARN manages cluster resources.
  • Spark: Processes data in-memory, making it 10–100x faster than MapReduce for iterative operations. Supports batch, streaming, SQL (SparkSQL), MLlib, and graph processing. Can run on HDFS, S3, or standalone.

In modern cloud architectures, Spark (via Glue or Databricks) largely replaces Hadoop MapReduce for processing, while S3 replaces HDFS as the distributed storage layer.

7
Explain window functions — ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD.
▼
  • ROW_NUMBER(): Assigns a unique sequential number to each row within a partition. No ties — always unique.
  • RANK(): Assigns rank with gaps when there are ties (1,1,3).
  • DENSE_RANK(): Assigns rank without gaps for ties (1,1,2). Best for financial rankings.
  • LAG(col, n): Returns value from n rows before the current row. I used this to detect previous billing amounts and compare with current to find anomalies.
  • LEAD(col, n): Returns value from n rows ahead. Useful for forecasting or detecting future state.
-- Example: Detect payment amount change vs previous month
SELECT account_id, month, amount,
       LAG(amount, 1) OVER (PARTITION BY account_id ORDER BY month) AS prev_amount,
       amount - LAG(amount,1) OVER (PARTITION BY account_id ORDER BY month) AS delta
FROM payments;
8
What is the difference between INNER JOIN, LEFT JOIN, and FULL OUTER JOIN? When would you use each?
▼
  • INNER JOIN: Returns only matching rows from both tables. Use when you only care about records that exist in both (e.g., customers who made a payment).
  • LEFT JOIN: Returns all rows from the left table, and matched rows from the right (NULLs where no match). Use for "show me all customers even if they have no orders."
  • FULL OUTER JOIN: Returns all rows from both tables. Use for reconciliation — I used this at Amdocs to compare two journal entry tables and find records missing in either side.
-- Financial reconciliation pattern I used at Amdocs:
SELECT COALESCE(a.account_id, b.account_id) AS account_id,
       a.billing_amount,
       b.payment_amount,
       CASE WHEN a.billing_amount IS NULL THEN 'Missing in billing'
            WHEN b.payment_amount IS NULL THEN 'Missing in payments'
            ELSE 'Mismatch' END AS issue_type
FROM billing_table a
FULL OUTER JOIN payments_table b ON a.account_id = b.account_id
WHERE a.billing_amount != b.payment_amount
   OR a.billing_amount IS NULL OR b.payment_amount IS NULL;
9
How do you optimise a slow SQL query?
▼
  • EXPLAIN / EXPLAIN ANALYZE: Always start here to understand the query plan and find sequential scans vs index scans.
  • Indexes: Add indexes on JOIN keys and WHERE clause columns. Use composite indexes where multiple columns are filtered.
  • Avoid SELECT *: Only fetch needed columns.
  • Filter early: Push WHERE conditions as early as possible; avoid filtering after JOINs on large datasets.
  • Partitioning: In Redshift/Databricks, use distribution and sort keys. In S3, partition by date/region to enable partition pruning.
  • Avoid functions on indexed columns: WHERE UPPER(name) = 'X' prevents index use. Use WHERE name = 'x' instead.
  • CTEs vs subqueries: Sometimes subqueries are evaluated once vs CTEs being re-evaluated — test both.
  • Redshift specific: Use DISTKEY on JOIN columns, SORTKEY on filter/order columns, and VACUUM ANALYZE regularly.
10
What is data normalisation? Explain 1NF, 2NF, 3NF.
▼
  • 1NF (First Normal Form): Each column has atomic (indivisible) values; no repeating groups. Every row is unique.
  • 2NF (Second Normal Form): 1NF + all non-key attributes are fully dependent on the entire primary key (no partial dependencies). Relevant for composite keys.
  • 3NF (Third Normal Form): 2NF + no transitive dependencies. Non-key attributes should only depend on the primary key, not on other non-key attributes.

In data warehouse design (OLAP), we often deliberately denormalise into star or snowflake schemas to optimise read performance over write efficiency.

How do you handle large datasets that don't fit in memory in Python?
▼
  • Chunking with Pandas: pd.read_csv(file, chunksize=100000) — process in batches and write results incrementally.
  • PySpark: Distributed computing — data is partitioned across a cluster, never all in memory on one node. My primary approach for millions of records at Amdocs.
  • Dask: Pandas-like API for parallel out-of-core computation when you don't want to set up Spark.
  • Columnar formats: Store data as Parquet or ORC in S3 — these enable column pruning and reduce I/O significantly.
  • Streaming: For real-time scenarios, process with Kinesis + Lambda rather than loading everything into memory.
12
Explain PySpark transformations vs actions. What is lazy evaluation?
▼
  • Transformations (lazy): Operations like filter(), map(), join(), groupBy() — they build a logical execution plan (DAG) but do NOT execute immediately.
  • Actions (triggers execution): count(), collect(), show(), write() — these trigger Spark to execute the entire DAG.
  • Lazy evaluation benefit: Spark can optimise the full execution plan (Catalyst optimiser) before running — pruning unnecessary operations, combining steps, and optimising joins.
df = spark.read.parquet("s3://bucket/billing/")
filtered = df.filter(df.status == "FAILED")  # Lazy
grouped = filtered.groupBy("account_id").count()  # Still lazy
grouped.show()  # ACTION — executes everything now

Write Python code to sort a list of strings alphabetically without using sorted().
▼
def sorting(lst):
    # Merge sort implementation - O(n log n)
    if len(lst) <= 1:
        return lst
    mid = len(lst) // 2
    left = sorting(lst[:mid])
    right = sorting(lst[mid:])
    return merge(left, right)

def merge(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i]); i += 1
        else:
            result.append(right[j]); j += 1
    result.extend(left[i:])
    result.extend(right[j:])
    return result

# Test
print(sorting(["banana", "apple", "cherry"]))
# Output: ['apple', 'banana', 'cherry']

15
What is the difference between a Data Lake and a Data Warehouse?
▼
  • Data Lake (S3 + Glue): Stores raw, unprocessed data in any format (JSON, CSV, Parquet, images). Schema-on-read — you define structure when querying. Cheap storage, flexible. Good for exploratory analytics, ML, and archival.
  • Data Warehouse (Redshift, Snowflake): Stores cleaned, structured, modelled data. Schema-on-write — structure defined before loading. Optimised for fast SQL analytics. Good for business reporting and dashboards.
  • Modern pattern (Lakehouse): Delta Lake / Apache Iceberg bridges both — raw data in S3 with ACID transactions and warehouse-like performance. Databricks on Delta Lake is an example.
16
How would you investigate latency in a data pipeline that was working fine for 2 years? (Actual Barclays interview question)
▼

This is a systematic debugging approach I'd use:

  • 1. Check monitoring dashboards first: CloudWatch metrics — identify which specific stage latency increased. Compare current vs historical baselines.
  • 2. Check for data volume change: Has the volume of input data grown significantly? S3 object counts, record counts per partition.
  • 3. Check for schema/format changes: Source systems changing data types or adding columns — can cause Glue/Spark serialisation overhead.
  • 4. Check infrastructure changes: Any Lambda concurrency limit changes? Glue DPU reduction? Step Function timeout changes?
  • 5. Check downstream dependencies: Is Redshift cluster under load? Network latency to RDS or external APIs?
  • 6. Check for skew: In Spark, data skew in one partition causes the overall job to wait. Check task duration in Glue job logs.
  • 7. Check change logs: Any recent deployments? IaC changes in Terraform? Config changes in GitLab?
Barclays tip: Start with data, not code. Most latency issues are data volume or infrastructure changes, not code bugs.

How would you migrate a legacy on-prem data warehouse to AWS?
▼
  • Assessment: Inventory existing tables, data volumes, query patterns, and dependencies.
  • Target architecture: S3 as data lake + Redshift as warehouse + Glue for ETL + Athena for ad-hoc queries.
  • Migration approach: Use AWS SCT (Schema Conversion Tool) to convert schemas; AWS DMS (Database Migration Service) for data movement.
  • Parallel run: Run old and new systems in parallel, compare outputs for validation.
  • ETL re-engineering: Replace SSIS/Informatica jobs with Glue PySpark jobs or Step Functions workflows.
  • Cutover: Freeze source, do final delta load, validate, switch traffic. Keep rollback plan ready.
  • Security: Replicate existing access controls using IAM + Lake Formation; encrypt data with KMS.
💡 Scenario-Based & Tricky Questions
25
A table has 100M rows. Your query is slow. What do you do?
▼
  • Run EXPLAIN ANALYZE to check the query plan — look for sequential scans, missing indexes, nested loop joins.
  • Check if appropriate indexes exist on JOIN and WHERE columns.
  • Consider partitioning — if filtering on date, partition the table by date.
  • In Redshift: check DISTKEY (even distribution across slices?) and SORTKEY (matches ORDER BY / WHERE columns?).
  • Materialize intermediate results using CTEs or temp tables to avoid re-scanning.
  • For S3-based queries (Athena/Glue): ensure data is partitioned and in Parquet format. Use partition pruning in WHERE clause.
  • Check for data skew in Spark — one partition taking 10x longer than others is a skew problem.
26
What would you do if your Glue job succeeds but data in Redshift looks wrong?
▼
  • Check the Glue job output logs for warnings (type coercions, null replacements).
  • Compare row counts between S3 source, Glue output, and Redshift target.
  • Check for silent data type conversions — e.g., floats truncated to int, strings silently nulled.
  • Verify the Redshift COPY command — was it using the right delimiter, encoding, or format?
  • Check if the job was using UPSERT vs INSERT logic incorrectly — duplicate key handling.
  • Run a sample comparison: pull 1000 records from source and target, compare side by side.

How do you ensure idempotency in your pipelines?
▼

Idempotency means re-running a pipeline produces the same result without duplicates or corruption.

  • Deduplication logic: Always check if a record already exists before inserting (MERGE / UPSERT patterns).
  • Partition-based overwrite: In Glue, write in overwrite mode per partition — re-running a day's data replaces that day's partition exactly.
  • Unique job run IDs: Track each pipeline execution with a unique run ID; skip already-processed batches using a metadata table.
  • Watermarking: Store the last processed timestamp/offset; on re-run, start from the same checkpoint.
  • Redshift MERGE/UPSERT: Use staging tables + MERGE to avoid duplicates on reload.
